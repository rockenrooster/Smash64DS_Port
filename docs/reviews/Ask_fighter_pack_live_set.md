# Hard problem: deriving a fighter's live-after-setup byte set

Status: open. Blocking P2 step 2 (four-fighter engine) and everything after it.
Written 2026-09-04 for external review.

## The decision I need made

P2 requires four *distinct* fighters resident at once. The four heaviest cost
404,336 bytes more than the P1 pair, against a measured free floor of 72,148
bytes. A previous external review (`docs/reviews/Design_DS_fighter_paging.md`)
refused runtime paging and prescribed an offline-generated, match-resident pack
instead. I accept that verdict.

What it did not answer, and what I am stuck on, is the step that actually
produces the pack:

> **How do you derive, mechanically and safely, the set of bytes a fighter's
> loaded files must still contain after setup completes — for all twelve
> fighters — when the reference graph crosses file boundaries and the failure
> mode is a wild pointer in a gameplay state no automated test reaches?**

I want a method, and a judgement on whether the pack is even the right shape
given the size of the hole. If the honest answer is "the pack cannot close
404,336 bytes and you need a different lever", say that instead.

## Measured numbers

Per-fighter main-closure allocation size, from
`include/nds/generated/nds_fighter_production.generated.h:10-21` (generated by
`scripts/fighters/generate_fighter_production_manifest.py` from the BattleShip
FTData tables, so these are the sizes `syTaskmanMalloc` is actually asked for,
not directory sums):

| Fighter | bytes | Fighter | bytes |
|---|---|---|---|
| Kirby | 204,208 | Captain Falcon | 102,448 |
| Yoshi | 146,928 | Samus | 85,296 |
| Fox | 119,040 | Pikachu | 80,528 |
| Link | 107,248 | Donkey Kong | 79,648 |
| Ness | 79,216 | Jigglypuff | 72,368 |
| Luigi | 57,104 | Mario | 54,048 |

- P1 shipped Mario + Fox: **173,088**.
- Worst four (Kirby, Yoshi, Fox, Link): **577,424**.
- Increase: **404,336**.
- Arena requested: `NDS_TASKMAN_ARENA_SIZE = 0x1a7000` = **1,732,608**
  (`src/port/diagnostics_mp_taskman_state.c:378`). The allocator fails soft —
  it hands back a smaller arena, and only `gNdsTaskmanArenaChosenSize` and
  `gNdsTaskmanArenaAllocFailCount` ever say so.
- Free floor over a full scripted VS-shell lap on the shipped ROM:
  **72,148 bytes** (Boundary arm `p2_shell_loop`).

So the shortfall is about 5.6x the entire remaining floor. This is not a tuning
problem.

Two further constraints that bound the answer:

- The ARM9 binary competes with the arena 1:1. A previous +14 KB of `.bss`
  stopped the ROM booting outright, and the four-distinct-kind roster's larger
  binary already cost the arena 36,864 bytes (AllocFail 9) before any of this
  work started. **Generated tables are not free**; a pack that trades 400 KB of
  heap for 400 KB of `.rodata` has moved the problem, not solved it.
- A separate four-CPU profile attributed roughly 41.9% of `.main` execution
  cycles to memory stalls, so the pack's *layout* is a performance lever as
  well as a capacity one.

## What is already settled — please do not re-derive these

1. **No runtime paging.** Already reviewed and refused.
2. **The bulk really is setup-only.** The port already has a native low-detail
   fighter image (`include/nds/generated/nds_native_fighter_image.generated.h`)
   that replaces raw vertex/display-list/texture decode for drawing. When the
   native path hits, the N64 display-list bytes and vertex arrays are not read
   per frame.
3. **Not everything is setup-only, and the exceptions are what make this hard.**
   A read-only probe of Kirby found post-setup readers of the raw files:
   - Copy-hat swap, on every Copy acquire, calls
     `ftParamSetModelPartDefaultID` then `ftParamResetModelPartAll`
     (`decomp/.../ft/ftchar/ftkirby/ftkirbyspecialn.c:128-129`), whose body
     reads `modelparts_desc[joint - Start]->modelparts[id][detail]` and pulls
     `dl / mobjsubs / costume_matanim / main_matanim / flags`
     (`decomp/.../ft/ftparam.c:776-782`).
   - Detail switching re-applies every joint
     (`ftParamSetModelPartDetailAll`), and the Low/High switch happens
     mid-match.
   - HUD, CSS and Results read `attr->sprites->stock_luts[fp->costume]`, which
     for Kirby points into the Model file.

## The wrinkle that makes this genuinely hard

**A fighter's live set is not a subset of its own files.** Verified directly in
`decomp/BattleShip-main/decomp/src/relocData/229_KirbyMain.c:251-261`:

```c
FTModelPart dKirbyMain_modelparts_desc_0x39C[2] = {
    { (Gfx*)&dLinkBoomerangModel_Joint_0x00F8_DisplayList, NULL, NULL, NULL, 0x00 },
    { (Gfx*)&dLinkBoomerangModel_Joint_0x00F8_DisplayList, NULL, NULL, NULL, 0x00 },
};

FTModelPart dKirbyMain_modelparts_desc_0x3C4[2] = {
    { (Gfx*)dFoxUnknown_DL, NULL, NULL, NULL, 0x00 },
    { (Gfx*)dFoxUnknown_DL, NULL, NULL, NULL, 0x00 },
};
```

Kirby's copy-hat table points at display lists inside **Link's** and **Fox's**
files. So "pack Kirby" is not a closed operation:

- If Link is not in the match, what does that pointer mean? The source keeps
  the donor file resident because the N64 had the RAM; we will not.
- Kirby's live set is a function of *the roster*, not of Kirby, so there are
  potentially 495 distinct four-fighter packs — which is why I cannot simply
  bake one per fighter and be done.
- Kirby is only the fighter I probed. I do not know how many other
  cross-fighter references exist, and enumerating them by hand across twelve
  fighters is exactly the work I am trying not to do.

## Sub-questions

1. **Derivation method.** What is the right mechanical way to compute the
   live-after-setup set? The candidates I see, none of which I am confident in:
   - *Static closure from the `.reloc` tables.* Every relocData file ships a
     `.reloc` listing its outgoing externs (`229_KirbyMain.reloc` has 100+ into
     KirbyModel). Sound, but it over-approximates to the whole file, which is
     the problem I started with.
   - *Dynamic witness.* Poison the abandoned range with a pattern after setup,
     then exercise every status, move, item and KO path and watch for reads.
     Sound only for the paths actually exercised, and the failure mode is
     precisely the rare path nobody scripted.
   - *Consumer-driven.* Enumerate the structures the runtime can reach
     (`FTModelPart` rows, `DObjDesc` trees, `MObjSub` chains, stock LUTs) and
     pack exactly those, treating the raw file as unreachable by construction.
     This is the one I lean toward, but it requires proving the enumeration is
     complete, and I do not know how to prove that.
   - Something else.
2. **Handling cross-fighter references.** Per-roster packs, a shared donor
   segment, rewriting the reference at bake time, or admitting the donor
   fragments into the borrowing fighter's pack? What does each cost when the
   donor *is* in the match and the bytes would otherwise be duplicated?
3. **Proving completeness.** What is the acceptance argument that the pack is
   complete, short of exhaustive playtesting? Is there a way to make an
   omission fail loudly and immediately at load time rather than as a wild
   pointer in a rare state?
4. **Is the pack even sufficient?** A single-fighter estimate suggested a pack
   of roughly 6-12 KB replacing 120,864 raw bytes for Kirby, but that figure is
   inference, not measurement — the selected-costume texture slice was never
   actually enumerated. If the real ratio is much worse, please say what the
   next lever is instead. VRAM residency, ROM-side streaming with a load-time
   guarantee, and reducing the number of simultaneously-distinct kinds are all
   on the table; I would rather be told the pack is the wrong shape now than
   after building the generator.
5. **Layout.** Given the 41.9% memory-stall figure, how should the pack be
   partitioned so the simulation-hot and render-hot working sets are
   contiguous? The prior review sketched SIM-HOT / RENDER-HOT / COLD; is that
   the right split, and what belongs in each?

## What I have not tried, and why

I have not built the poison-and-witness harness, because I do not want to spend
a build cycle proving out a method I am not confident is the right primary one —
the rare-path blind spot looks fatal to it in that role, though it may be a good
secondary check.

I have not built a per-roster pack generator, because 495 packs is obviously
wrong and I would rather know the right factoring first.
