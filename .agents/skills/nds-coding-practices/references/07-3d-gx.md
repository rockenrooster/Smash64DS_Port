# GX 3D Rendering Practices

## Treat GX as a persistent state machine

The DS geometry engine consumes commands through a FIFO. It retains matrix and
draw state until changed. A renderer is correct only when it establishes every
state it depends on rather than inheriting accidental state from a previous
owner.

Explicitly own:

- matrix mode and matrix-stack depth;
- projection, position/modelview, texture, and vector matrices;
- primitive begin/end state;
- polygon format;
- texture and palette binding;
- texture parameters and coordinates;
- color, normal, material, light, and shininess state;
- viewport, clear state, alpha/depth behavior;
- frame-finalization and swap order.

## Hard capacity limits

Polygon RAM and vertex RAM bound one frame at 2048 polygons and 6144
vertices. There is no queueing beyond that: geometry submitted after either
fills is dropped for the rest of the frame, and GXSTAT reports the overflow.
Budget worst-case scenes in the asset pipeline and verify at runtime in debug
builds — `glGetInt(GL_GET_POLYGON_RAM_COUNT, ...)` and
`GL_GET_VERTEX_RAM_COUNT` read the counts once the frame's geometry has
completed — rather than discovering the cap as vanishing geometry.

The render engine has no full frame buffer: it rasterizes in lockstep with
scanout, holding only a small scanline lead. Per-scanline raster capacity is
finite, so rows crossed by too many polygons or too much translucent fill can
drop or corrupt just those lines. Per-line polygon concentration and overdraw
are therefore first-class budgets alongside total polygon count.

## Initialization

A conventional current libnds shape is:

```c
#include <nds.h>

static void init_3d(void)
{
    videoSetMode(MODE_0_3D);
    vramSetBankA(VRAM_A_TEXTURE);

    glInit();
    glEnable(GL_ANTIALIAS);
    glClearColor(0, 0, 0, 31);
    glClearPolyID(63);
    glClearDepth(GL_MAX_DEPTH);
    glViewport(0, 0, 255, 191);

    glMatrixMode(GL_PROJECTION);
    glLoadIdentity();
    gluPerspective(70, 256.0f / 192.0f, 0.1f, 40.0f);

    glMatrixMode(GL_MODELVIEW);
    glLoadIdentity();
}
```

This is an API-composition example, not a recommendation to calculate floating
point every frame. Build fixed matrices or precompute camera constants in
performance-sensitive code.

## Matrix discipline

### Set matrix mode deliberately

Before every matrix operation sequence, set the expected mode. A helper that
assumes the caller left `GL_MODELVIEW` active creates action-at-a-distance bugs.

### Balance stacks

Every push must have exactly one pop on all control-flow paths. Track expected
stack depth in debug builds and assert scene boundaries return to the baseline.
Do not use a push per object when a cheaper load/multiply strategy is available
and stack capacity is tight.

### Separate coordinate conventions

Document:

- axis orientation and handedness;
- world, view, model, and texture matrix order;
- fixed-point format of vertices/matrices;
- near/far and depth convention;
- normal scaling/normalization assumptions.

Porting another renderer without reconciling these conventions often produces
mirroring, reversed winding, bad lighting, or depth errors.

## Primitive correctness

- Pair each `glBegin` with `glEnd`.
- Do not change state that is illegal or ambiguous inside a primitive.
- Validate vertex counts for triangles/quads/strips.
- Account for triangle-strip parity when culling or converting meshes.
- Preserve or deliberately regenerate winding after coordinate transforms.
- Keep index and vertex bounds checked before command emission.

A missing vertex or malformed packed command can desynchronize the entire
stream and make later geometry appear corrupt.

## State scopes

For multiple draw owners, choose one of two designs:

1. **Renderer-enforced baseline:** every owner sets all relevant state before
   drawing.
2. **Explicit state scope:** wrapper records/restores the exact state contract.

Do not rely on undocumented convention such as “the previous model always
leaves white color and texture matrix identity.”

A practical material key can include polygon format, texture ID, palette ID,
color/material flags, and blend/depth mode. Sorting by this key can reduce state
changes, but preserve transparency ordering requirements.

## Texture practices

- Convert textures offline to a supported DS format.
- Validate power-of-two/dimension and format constraints in the converter.
- Allocate texture and palette VRAM through one owner.
- Bind texture and palette together; stale palette state can look like corrupt
  texture data.
- Establish UV fixed-point scale and wrapping deliberately.
- Do not upload or quantize textures in the visible draw loop.
- Invalidate texture handles when VRAM layout generation changes.

When using a library texture allocator, do not also compute raw offsets behind
its back.

## Lighting and normals

- Use the normal format expected by the GX API/hardware.
- Transform normals with the correct vector matrix behavior.
- Avoid zero-length normals.
- Set light/material state explicitly for lit owners.
- Disable or override lighting for unlit owners rather than relying on color
  alone.
- Precompute static normals and material tables offline.

## Polygon/depth/alpha state

Set polygon format per material or batch. Validate:

- polygon ID allocation and shadow/stencil-like uses;
- alpha value and alpha-test policy;
- back/front-face culling relative to winding;
- depth test/update behavior;
- translucent ordering;
- fog and edge-marking state;
- far-plane/one-dot behavior where relevant.

The DS translucent pipeline has hardware-specific ordering and depth behavior;
do not assume desktop OpenGL semantics.

## Frame finalization

Prepare and submit the scene, then finalize once according to the project's
libnds/GX path, commonly with `glFlush(...)`. Do not call frame swap/finalization
inside each model renderer.

A typical frame separates:

1. gameplay/update;
2. visibility and draw-list construction;
3. GX command submission;
4. frame finalization;
5. VBlank/presentation synchronization and 2D commits.

The exact ordering may be project-specific, but it must have one owner.

## 3D on both screens or at reduced rate

There is one 3D engine and it draws into main BG0 at display rate.
Dual-screen 3D and reduced-rate 3D presentation are built from display
capture: render, capture into a VRAM bank, and show the captured bitmap while
the engine does other work (see `06-2d-video-bg-oam.md`). The capture bank,
the extra VBlank sequencing, and any screen-swap schedule are part of the
renderer design; budget them like any other owner.

## FIFO and geometry stalls

A write to GX can block when the FIFO is full or when the geometry engine is
backpressured. Therefore “CPU time in renderer” may actually be wait time.
Distinguish:

- command construction;
- command writes;
- FIFO wait;
- geometry completion/swap wait;
- raster/fragment limitations.

Reducing polygons may not help if command count, matrix churn, state changes, or
fill dominates.

## Display lists and prebuilt command streams

Prebuilding immutable GX commands can remove interpretation and call overhead,
but only when:

- command format and alignment are correct;
- all embedded values use the required packed representation;
- mutable fields have bounded patch locations;
- source storage remains alive and visible until consumed;
- cache is flushed before DMA/GX consumption;
- command ownership and FIFO timing are correct;
- the path is verified to execute on the target build.

A large copy-and-patch stream can be slower than compact direct submission.
Measure the full owner.

## Geometry/data design

Prefer:

- DS-native packed vertices/normals/UVs;
- dense material and matrix indices;
- setup-time mesh conversion;
- static display data for immutable geometry;
- coarse visibility tests before per-part work;
- material/state sorting when transparency permits;
- specialized renderers for dominant fixed assets.

Avoid per-frame generic scene-graph traversal, dynamic allocation, float matrix
construction, texture conversion, and pointer-heavy material lookup.

## Common failures

### Later objects inherit wrong color or texture

The previous owner changed persistent state. Set the full material baseline for
each batch.

### Geometry disappears after one model

Look for unbalanced matrix stacks, missing `glEnd`, malformed display-list
counts, invalid texture state, or polygon culling/winding mismatch.

### Model is mirrored or inside-out

Reconcile coordinate handedness, matrix order, winding, and strip parity.

### Geometry vanishes only in heavy scenes

Polygon or vertex RAM overflowed and the excess was dropped for the frame.
Read the RAM counts in a debug build and cut worst-case submission, not the
average.

### Isolated glitch or gap lines on heavy rows

Per-scanline raster capacity was exceeded. Reduce per-line polygon crossings,
translucent stacking, or overdraw on those rows; total triangle count may be
irrelevant.

### Performance worsens after “fewer polygons”

Measure matrix/state command count, FIFO waits, draw-owner overhead, overdraw,
and patch/copy cost. Triangle count is only one mechanism.

### Textures corrupt after scene switch

Likely stale VRAM-layout generation, palette binding, allocator reset, or upload
still in flight.

## Review checklist

- [ ] Every draw batch establishes required persistent state.
- [ ] Worst-case polygon/vertex RAM counts are verified under the 2048/6144
      caps, not assumed.
- [ ] Matrix modes and stack depths are balanced on all paths.
- [ ] Primitive counts, strip parity, winding, and indexes are valid.
- [ ] Texture and palette residency share one allocator/generation.
- [ ] Frame finalization has one owner and occurs once.
- [ ] GX waits are distinguished from CPU construction cost.
- [ ] Offline data uses DS-native packed formats.
