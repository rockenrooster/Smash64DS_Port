PREMISE RE-VERIFIED FROM THE ASSET, NOT INHERITED
======================================================================
decomp/BattleShip-main/decomp/assets/us/relocData/85.vpk0.bin, beam list 0x2890:

  0x28a0  FCFFFFFF FFFDF2F9   G_SETCOMBINE
  0x28a8  FA000000 FFFFFFFF   G_SETPRIMCOLOR = 255,255,255,255
  0x28b8  F5800200 00090230   G_SETTILE render tile: fmt=4 (I), siz=0 (4b)

Decoded in BOTH cycle layouts -- they are identical, so the recogniser fires
whatever G_SETCYCLETYPE says:

  colour  a=15 b=15 c=31 d=3    -> 0, 0, 0, PRIMITIVE
  alpha   a=7  b=7  c=7  d=1    -> 0, 0, 0, TEXEL0

So rgb = PRIMITIVE (white), alpha = TEXEL0, on an I4 image. The cycle-67
diagnosis is confirmed exactly; nothing was taken on trust.

Note the zero encodings are field-width-specific. G_CCMUX_0 is 31 and each
colour field masks it to its own width: 15 in the 4-bit a and b fields, 31 in
the 5-bit c field, 7 in the 3-bit d field. The header had names for the a/b and
d widths only; NDS_RENDERER_CCMUX_ZERO_C was added so a gate cannot compare a c
field against the a/b encoding.

======================================================================
THE CHANGE
======================================================================
src/nds/nds_renderer.c

1. NDS_RENDERER_PRIM_ENV_BLEND_PRIM_RGB_TEXEL0_ALPHA (3u), a third arm on
   ndsRendererHardwarePrimEnvTexel0BlendMode. The existing BLENDPE lerp gate is
   UNCHANGED -- it became the body of an `if` instead of an early-out `if not`,
   with its two alpha arms intact inside it, and the degenerate constant form is
   a SEPARATE branch below. The gate was not widened.

2. ndsRendererHardwarePrimRgbTexel0Alpha: emits PRIM's RGB with the source
   intensity as the alpha bit. ndsRendererHardwareConvertI is NOT touched -- it
   serves every I-format texture in the game, and the coverage this combine wants
   is still recoverable from any one of the RGB5 lanes it wrote. Coverage
   quantises to one bit at >= 16 of 31 (round to nearest).

3. Cache key: its OWN bit, NDS_RENDERER_HW_TEXTURE_KEY_PRIM_RGB_TEXEL0_ALPHA
   (1u << 30). THE EXISTING BIT WAS NOT ENOUGH. Modes 1 and 2 both bake through
   ndsRendererHardwareBlendPrimEnvTexel0, so one flag distinguished "baked" from
   "raw" and that sufficed. Mode 3 bakes differently, so sharing the flag would
   let a beam and a BLENDPE surface with equal prim/env collide on one entry and
   serve whichever converted first. PRIM RGB was already keyed (combine_w0) and
   stays keyed because it is now the texel colour itself; ENV is dropped
   (combine_w1 = 0) because this combine never reads it and keying on it would
   force a re-bake whenever an unrelated list moved the env colour.
   Bit 30 is free: key.flags holds render_tile_flags in bits 0-7 and
   (load_kind << 8), and load_kind's largest value is 1u << 6.

4. ndsRendererHardwareBlendModeKeepsTexelCoverage, used at
   ndsRendererHardwareAlpha and ndsRendererHardwareAlphaUsesVertex. BEYOND THE
   BRIEF'S TWO EDITS, and stated as such: those two sites keyed on
   SOURCE_ALPHA alone, but SOURCE_ALPHA and mode 3 have BYTE-IDENTICAL alpha
   muxes and differ only in colour, so an alpha-side decision must treat them
   the same or the new mode multiplies vertex alpha into coverage the texel
   already carries. Both sites are unreachable for this beam (othermode_l
   0x552078 takes their opaque early return first), so this closes a latent
   asymmetry rather than fixing a measured defect.

THE CEILING, MEASURED RATHER THAN ASSERTED
======================================================================
The DL texture upload is GL_RGBA at nds_renderer.c:14834 -- RGB555 + ONE alpha
bit. So the beam is white with a HARD EDGE, not the source's 32-level fade.
That is visible in the AFTER histogram: 45.2% of changed pixels are exactly
255,255,255 with no intermediate coverage between them and the background.

Threshold choice: >= 16 of 31, round to nearest, not "any non-zero". A
threshold of 1 would promote the whole faint outer ramp to fully opaque and
draw a beam WIDER than the source. This is a judgement inside a 1-bit
constraint and it is the owner's to overrule.

WHAT A5I3 WOULD COST, scoped honestly and NOT built:

The generic helper already exists and is already parameterised by format and
palette size: ndsRendererHardwarePrepareIFCommonAtlas (:10269), with wrappers
...PrepareIFCommonCloudAtlas -> GL_RGB8_A5, 8 entries (:10343) and
...PrepareIFCommonA3I5Atlas -> GL_RGB32_A3, 32 entries (:10352). A5I3 is LIVE
today for the cloud atlas. (The particle/effect atlas moved A5I3 -> A3I5 on
2026-08-03 because 8 SHARED palette entries could not hold Fox's reflector blues
alongside every other effect's greys, :11508-11523. That history is the argument
against sharing one A5I3 palette across cached DL textures -- and it does not
apply to a beam that needs exactly one colour.)

Routing the CACHED DL path to A5I3 needs four coupled changes:
  1. sNdsRendererHardwareTextureScratch is `static u16` (:3608) and the whole
     convert loop, the row staging and the unique-row compaction write u16
     RGBA5551. A5I3 is one byte per texel.
  2. NDSRendererHardwareTextureCacheEntry (:3427) carries no format; the upload
     hardcodes GL_RGBA. Format becomes per-entry.
  3. Each entry needs its own palette, and glColorTableEXT binds to the
     CURRENTLY BOUND name -- so palette upload moves into the bind path.
  4. VRAM accounting and eviction assume two bytes per texel.

DOES THE CACHE GENUINELY NEED PER-ENTRY FORMAT? No -- one dedicated slot would
do, and it is much cheaper. The atlas helpers already live entirely outside the
cache (they set sNdsRendererHardwareActiveTextureEntry = NULL). The work would
be a fill callback converting the I4 nibble plane to A5I3 bytes
((alpha5 << 3) | index, alpha5 = nibble<<1 | nibble>>3, palette entry 1 =
white), ONE prepare at load rather than per frame, a bind-time redirect keyed on
the SEMANTIC discriminator already in hand (blend mode 3 + format I + size 4b,
not a stage address or DL pointer), and a one-entry memo of the prepared name.
That generalises to any list carrying this combine instead of hard-coding the
beam.

Recommendation stated, not taken: dedicated slot, not per-entry cache format.
Whether the hard edge needs fixing at all is the owner's call.

CYCLE-66 LATCH PREDICTION -- CONFIRMED, WITH A CONTROL THAT CAN FAIL
======================================================================
The prediction was: the beam's list emits no G_SETOTHERMODE_L of its own, so
Out == In, while a list that carries its own mode reads Out != In.

  KOLATCH tag=rebirth-halo   in=0x552078 out=0x552078 same=1 submits=72
  KOLATCH tag=post-star-3s   in=0x552078 out=0x552078 same=1 submits=204
  KOLATCH tag=late-match     in=0x5049d8 out=0x552078 same=0 submits=1272
  KOLATCH tag=results        in=0x504341 out=0x504340 same=0 submits=1970
                                                        (c66 ROM run)

same=1 at both halo tags, and same=0 elsewhere in the SAME run -- so the latch
can differ and same=1 is a measurement, not a stuck counter. submits=0 with
in=out=0 at the two earliest tags is the engagement guard doing its job: that
is "the latch never ran", not "the mode was zero".

0x552078 decodes to ac=0, zmode=OPA, forcebl=0, cvgxalpha=0 -- an opaque render
mode, which is also why the two alpha-side call sites in change 4 above are
unreachable for this beam.
