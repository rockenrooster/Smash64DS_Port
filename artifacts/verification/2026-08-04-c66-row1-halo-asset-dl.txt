Row 1 (revival platform) -- does the RebirthHalo's baked asset display list
carry a G_SETOTHERMODE_L (0xE2)?

ANSWER: YES -- 16 of them, but ONLY on one of the effect's two dl_link buckets.
The bucket that draws the white beam carries none, and in the source that
bucket is a SEPARATE RDP output stream with its own render-mode preamble.

Cycle 66, 2026-08-04. No build and no emulator were spent on this. Every number
below is decoded from read-only bytes on disk.

======================================================================
WHERE THE 0xE2 WORDS ARE
======================================================================
entry[2] / list_id 0 -> wrapper 0x27e8 -> four leaves 0x2388 0x24a0 0x25b8 0x26d0.
Each leaf is bracketed identically. Leaf 1 verbatim:

  0x2398: e3001001 00008000  SETOTHERMODE_H  cycle type
  0x23a0: e2001e01 00000001  SETOTHERMODE_L  shift=0  len=2   ALPHACOMPARE=1 (G_AC_THRESHOLD)
  0x23a8: e200001c 00553078  SETOTHERMODE_L  shift=3  len=29  RENDERMODE
  0x23b0: fc127e24 fffff3f9  SETCOMBINE      rgb=(TEXEL0-0)*SHADE+0, a=TEXEL0
  ... CI4 40x16 texture, 16-entry RGBA16 TLUT at 0x918, texels at 0xa40 ...
  0x2480: e3001001 00000000  SETOTHERMODE_H
  0x2488: e2001e01 00000000  SETOTHERMODE_L  ALPHACOMPARE=0 (G_AC_NONE)
  0x2490: e200001c 00552078  SETOTHERMODE_L  RENDERMODE (restore)
  0x2498: df000000 00000000  ENDDL

  0x00553078 = G_RM_AA_ZB_TEX_EDGE | G_RM_AA_ZB_TEX_EDGE2
      low half 0x3078 = AA_EN|Z_CMP|Z_UPD|IM_RD|CVG_DST_CLAMP|ZMODE_OPA
                        |CVG_X_ALPHA|ALPHA_CVG_SEL
      high half 0x0055 = GBL_c1|GBL_c2 of (CLR_IN, A_IN, CLR_MEM, A_MEM)
  0x00552078 = the same without CVG_X_ALPHA = G_RM_AA_ZB_OPA_SURF|..._SURF2

  4 leaves x (1 alpha-compare set + 1 rendermode set + the two restores) = 16
  G_SETOTHERMODE_L commands. That is the whole count; there are none anywhere
  else in the halo's reachable lists.

======================================================================
WHY list_id 1 HAS NO MODE OF ITS OWN, AND WHAT THAT MEANS FOR THE PORT
======================================================================
list_id is not an ordering hint. In the source it selects one of FOUR separate
RDP output streams:

  objdisplay.c:1716-1739, gcDrawDObjTreeDLLinks
      while (dl_link->list_id != ARRAY_COUNT(gSYTaskmanDLHeads)) {
          ...
          gSPDisplayList(gSYTaskmanDLHeads[dl_link->list_id]++, dl_link->dl);
          dl_link++;
      }

Each head is its own command stream with its own render-mode preamble, written
by the effect display brackets:

  efdisplay.c:15-21  efDisplayXLUProcDisplay -> gSYTaskmanDLHeads[1]
      gDPSetRenderMode(G_RM_AA_ZB_XLU_SURF, G_RM_AA_ZB_XLU_SURF2)
      gDPSetAlphaCompare(G_AC_NONE)
  efdisplay.c:5-12   efDisplayCLDProcDisplay -> gSYTaskmanDLHeads[1]
      gDPSetRenderMode(G_RM_CLD_SURF, G_RM_CLD_SURF2)
  efdisplay.c:66-77  efDisplayZPerspAAXLUProcDisplay -> gSYTaskmanDLHeads[0]
      sets AA_ZB_XLU, draws particles, RESTORES G_RM_AA_ZB_OPA_SURF (line 76)

So on the halo's link (dEFManagerRebirthHaloEffectDesc.dl_link = 10,
efmanager.c:1651) head[0] ends the bracket at G_RM_AA_ZB_OPA_SURF, and head[1]
carries a translucent mode written by the XLU/CLD brackets on their own links.
The halo's list-0 leaves do not care -- they set their own mode. Its list-1
beam depends entirely on head[1] already being translucent.

The port collapses all four heads into ONE immediate GX stream:
  reloc_backend_renderer_dl.c:9578-9592, ndsRendererAdapterSubmitStageDObjNode
      for (i = 0; i < GC_COMMON_MAX_DLLINKS; i++, dl_link++) { ...
          ndsRendererAdapterSubmitStageDL(dobj, dl_link->dl, ...); }
Every dl_link entry is submitted back to back into the same state, and every
effect submit first overwrites the mode with the captured LAYER value:
  reloc_backend_renderer_dl.c:9243-9246
      if (sNdsRendererAdapterEffectOtherModeValid != 0u)
          render_stats->othermode_l = sNdsRendererAdapterEffectOtherModeL;

The beam therefore runs with head[0]'s opaque mode, and:
  nds_renderer.c:8304-8313, ndsRendererHardwareAlpha
      if alpha-compare != THRESHOLD and !FORCE_BL and !CVG_X_ALPHA
         and ZMODE != XLU  ->  return 31u
G_RM_AA_ZB_OPA_SURF satisfies all four, so the beam's every polygon is
submitted at POLY_ALPHA(31) -- fully opaque -- and its alpha ladder, which is
the only thing that gives the beam its shape, is discarded.

======================================================================
WHAT IS PROVEN AND WHAT IS NOT
======================================================================
PROVEN, from bytes:
  - the halo's asset DL does contain G_SETOTHERMODE_L; 16 words, all on
    entry[2]/list 0, setting TEX_EDGE and restoring OPA_SURF around each leaf.
  - the white beam (entry[1]/list 1) contains none, is unlit, is rgb=PRIM white
    with alpha=TEXEL0 over an I4 fade ladder, and in the source draws into a
    different RDP stream from the leaves.
  - the port submits both buckets into one stream and forces the layer mode at
    the head of every effect DL submit.
  - ndsRendererHardwareAlpha returns 31 for that mode.

NOT PROVEN this cycle -- the next cycle should measure, not assume:
  - which of the three lists produces the pixels the owner photographed. The
    measured greys 0/36/223 are consistent with the beam's ladder rendered with
    intensity in RGB instead of alpha, but no capture separates the three
    lists yet. gNdsEffectDLSubmitOtherModeIn/Out/Count (added this cycle) are
    the instrument: the beam must show Out == In, a leaf must show Out != In.
  - what DS texture format the beam's I4 image is uploaded as. If it lands as a
    grey-ramp colour texture rather than white+alpha, honouring the render mode
    alone will not restore the beam; both halves have to be right.
  - the correct fix shape. Making a list-1 DL inherit head[1]'s mode rather
    than head[0]'s is a renderer-seam change with blast radius beyond this
    effect, and is not a one-line edit. It is not attempted here.
